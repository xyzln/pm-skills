# 交付产物（Shipping Artifacts）：让 AI 写的代码可被评审的文档

## 目的（Purpose）

AI 智能体写代码很快，却不留下关于*意图*的持久记录——系统本该做什么、谁有权做什么、密钥放在哪儿、哪些规则真正被验证过。没有这份记录，任何人（以及任何审计智能体）都无法判断代码能否安全上线。本技能定义了那一小组能把可评审性找回来的文档。

这些文档放在 `/documentation/` 下，写给两类读者：人类评审者和下一个 AI 编程智能体。它们是后续每次审计中**预期状态**的那一半——安全或性能评审的质量，取决于它能拿什么意图来和代码比对。

## 这套文档怎么组织

这套文档**不是**一张固定清单——它是一个精简的**核心**，加上只在对应用能真实存在时才添加的**条件文档**。

- **核心文档**——每个可评审的应用都有这些面，所以始终产出。
- **条件文档**——只有应用确实具备该能力时才加。没有的话，在 `architecture.md` 里写一行（如「没有定时任务——故无 `cron.md`」），而不是编一份空文档。可评审性来自诚实的地图，而「我们不做 X」也是地图的一部分。
- 多数文档由 `/document-app` 从代码反向梳理而成。唯一例外是 `tests.md`，它由 `/derive-tests` *从其他文档推导*而来——它是验证地图，不是某个子系统的说明书。

对现状要极度诚实，但不必疑神疑鬼。活儿是画一张准确的地图，不是开一张健康证明。每份文档都短、多表格多要点、不写泛泛的理论。

## 核心文档

每条包含：文件 · 一句话用途 · 必须记录什么 · 评审者怎么用。

1. **`architecture.md`**——系统是什么、各部件怎么挂在一起。
   - 必须记录：产品概览 + 关键假设；技术栈；认证/会话/声明如何端到端流转；信任边界（如 service-role vs. 客户端）；一份简短的**已知风险/假设**清单（每条都附上它在代码中出现的位置，而不是通用清单勾选）；一份「相关文档」索引，列全其他所有产出文档。
   - 评审者用法：根文档——其他一切都从这里交叉引用。

2. **`flows.md`**——权限和副作用真正被触发的那些旅程。
   - 必须记录：每条承重流程写成「角色 + 前置条件 + 成功结果」；跨 UI → 服务端 → 数据 → 任务 → 供应商 → 智能体的逐步时序；**每个受保护步骤的授权（authz）检查**（哪个声明/角色/作用域、针对哪个资源、以及预期的*拒绝*分支）；**信任边界穿越**（浏览器→服务端、服务端→供应商、任务→应用、智能体→工具、webhook→应用）；每步引发的状态变更与副作用（写入、排队邮件、触发任务、外呼）。
   - 评审者用法：静态 `permissions.md` 矩阵给不了的运行时视角——授权在*哪儿*、按*什么顺序*强制执行，以及哪儿可能被跳过。
   - **反 PRD 规则：**不碰权限、数据完整性、外部副作用、资金、隐私或运行安全的流程，不该出现在这里。这是安全/运维地图，不是功能规格。

3. **`permissions.md`**——谁有权做什么。
   - 必须记录：角色/声明；作用域从哪儿派生（token 还是数据库）；一张「资源 × 操作 × 角色」矩阵；哪些表有行级安全（RLS）、哪些靠代码强制检查。
   - 评审者用法：访问控制审计拿代码比对的基线。`flows.md` 展示它如何运转；这份是静态参考。

4. **`variables.md`**——配置与密钥，按风险映射。
   - 必须记录：一张「名称 · 使用方 · 作用域（服务端/客户端）· 来源 · 轮换 · 风险」表；明确确认没有任何密钥被打包进客户端；一份上线前检查清单。
   - 评审者用法：密钥/个人信息（PII）泄露的面，以及故障响应期间的轮换计划。

5. **`tests.md`**——验证地图：哪些已成文的规则真正被测到、哪些只是提议、哪些什么都没测。
   - 必须记录，分三个界限清晰的小节，防止地图被误读成一片绿：
     - **现有覆盖**——*今天*就在仓库里的测试，每条都挂到它钉住的规则上（让地图反映现实，而不是愿望清单）。
     - **提议中的测试**——建议写但还没写的用例，标注**测试类型**（自动化单元/集成 · 有监护的线上 · 人工评审）。
     - **缺口**——完全没有任何验证的已成文规则，按「违反它会暴露什么」排序。
   - 每一行包含：用例 → 规则 → 预期行为（含拒绝/负向分支）→ 证据来源（文档 + 代码）→ 状态（已有 / 提议 / 无）。同时标注哪些检查是 CI 强制、卡住合入 `main` 的。
   - 评审者用法：「已成文 == 已实现」的运维版——它显示其他文档声称的每条规则，今天是真有测试钉住、只是提议、还是压根没验证。
   - 由 `/derive-tests` 产出（不是 `/document-app`），因为它从其他文档和现有测试套件推导而来，而不是从某个子系统读出来。

## 条件文档（仅在对应用能存在时包含）

6. **`emails.md`**——系统发出的每一类通知。*仅当应用发送交易型或自动化邮件时才包含。*
   - 必须记录：队列 → 处理器 → 供应商的路径；模板及其接受的变量；重试/退避行为；发送失败时去哪儿看。
   - 评审者用法：发现未校验的模板输入和个人信息（PII）暴露边界。

7. **`cron.md`**——所有定时任务及如何安全地运维它们。*仅当存在定时或后台任务时才包含。*
   - 必须记录：一张清单表（任务 → 调度 → 函数 → 密钥 → 限额 → 重试）；每个任务如何保持幂等；内部调用如何认证；去哪儿看最近运行记录。
   - 评审者用法：找出可伪造的触发口和没有上限的后台任务。

8. **`seo.md`**——单页应用（SPA）如何处理 SEO 和社交预览。*仅当存在公开/可收录或面向爬虫的路由时才包含。*
   - 必须记录：预览方案（静态 meta / 预渲染 / 边缘 HTML）；一张「路由 → 是否需要 SEO → 仅公开数据」表；动态元数据如何消毒；爬虫与人类的路由分流。
   - 评审者用法：抓住「仅公开数据」违规和爬虫路由上的元数据注入。

9. **`automation.md`**——内嵌智能体及其他自动化路径。*仅当应用内嵌 AI 智能体、大模型（LLM）工作流、工具调用、webhook 或外部自动化时才包含。*
   - 必须记录，针对每个自动化/智能体：触发器 + 负责人 + 是自动运行还是需批准后运行；它可以读取哪些输入、**可以调用的确切工具/API**（工具面本身就是一道硬护栏）；**引导**（steering，即提示词）放在哪儿，与**非提示词的硬护栏**如何区分；回传给应用的**输出契约**（schema、校验、失败处理）；**应用侧拥有的副作用 vs. 智能体侧给出的建议**；以及各类控制手段——审批闸门、审计/时间线日志、限流、重试、急停开关。
   - 评审者用法：让隐藏的自动化路径显形，并划出智能体*提议*与应用*强制*之间的界线——这是现代 AI 构建应用中风险最高的面。

## 备注（Notes）

- 每产出一份文档，都要在 `architecture.md` 的「相关文档」小节里加上它自己的引用，让整套文档始终可被发现。
- 不适用的条件文档直接跳过，用一行说明，而不是编造内容。
- 这些文档里不放示例和成品的模板——它们描述的是*这个*系统，不是通用方法。
- 智能体操作上下文文件（`AGENTS.md` 一类）是*另一种*产物——它是从这些文档推导出的指令，不是系统文档。它在交接步骤由 `/ship-check` 产出，不是这里。
- `tests.md` 由 `/derive-tests` 产出；其余由 `/document-app` 产出。
- 不要写「更新日期」行；文件的历史记录才是事实来源。
