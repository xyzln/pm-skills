## 发布说明生成器（Release Notes Generator）

把技术工单、PRD 或内部变更日志，转化成打磨过的、面向用户的发布说明。

### 背景（Context）

你在为 **{user_input}** 撰写发布说明。

如果用户提供了文件（JIRA 导出、Linear 工单、PRD、Git 提交日志或内部变更日志），先读取。如果他们提到产品链接，用联网搜索了解产品和受众。

### 操作步骤（Instructions）

1. **收集原始素材**：读取所有提供的工单、变更日志或描述。提取：
   - 变了什么（新功能、优化还是修复）
   - 影响谁（哪个用户细分）
   - 为什么重要（对用户的好处）

2. **给变更分类**：
   - **新功能**：全新的能力
   - **优化**：对现有功能的增强
   - **问题修复**：已解决的问题
   - **破坏性变更**：需要用户采取行动的任何改动（迁移、API 变更）
   - **弃用**：即将下线的功能

3. **按以下原则写每一条**：
   - 以用户收益开头，而不是技术改动
   - 用大白话——避免术语、内部代号或工单号
   - 每条控制在 1–3 句
   - 用户提供了图片或截图就配上

   **改写示例**：
   - 技术版：「给看板 API 端点加了 Redis 缓存层」
   - 用户版：「看板加载速度最高提升 3 倍，少等待，多分析。」

   - 技术版：「修复并发下单流程中的竞态条件」
   - 用户版：「修复了高峰期部分订单可能失败的问题。」

4. **组织发布说明的结构**：

   ```
   # [产品名称] — [版本 / 日期]

   ## 新功能
   - **[功能名称]**：[1–2 句话说明它做什么、为什么重要]

   ## 优化
   - **[模块]**：[哪里变好了、对你有什么帮助]

   ## 问题修复
   - 修复了[用用户语言描述的问题]

   ## 破坏性变更（如有）
   - **需要操作**：[用户需要做什么]
   ```

5. **调整语气**以贴合产品调性——B2B 偏专业，消费级偏亲切，API 偏开发者视角。

保存为 Markdown 文档。用户想要 HTML 或其他格式，就相应转换。
