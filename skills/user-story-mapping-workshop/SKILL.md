## 目的

引导产品经理（PM）创建用户故事地图：先就系统、用户、工作流与优先级提出自适应问题，再生成一张包含主干（活动）、用户任务与发布切片的二维地图。用于把扁平的需求池转化为可视化的故事地图——讲清全局、发现缺失功能、支撑有意义的发布规划——避免故事沦为"脱离上下文的碎料（context-free mulch）"，与整体系统叙事失去关联。

它不是需求池生成器，而是一个可视化沟通框架：横向按用户工作流组织工作，纵向按优先级组织工作。

## 核心概念

### 什么是用户故事地图？

故事地图（Jeff Patton）把用户故事组织在**两个维度**上：

**横轴（从左到右）：** 活动按叙事/工作流顺序排列——就是你向别人讲解这个系统时的叙述顺序

**纵轴（从上到下）：** 每个活动内部的优先级，最必要的任务放在最上面

**结构：**
```
主干（活动，横向贯穿顶部）
↓
用户任务（按优先级纵向排列）
↓
细节/验收标准（位于底部）
```

### 关键原则

**主干（Backbone）：** 核心活动构成系统的结构骨架——它们之间不排优先级，而是叙事流本身。

**行走骨架（Walking Skeleton）：** 所有活动中优先级最高的任务合起来构成最小可行产品——最小的端到端功能闭环。

**肋骨（Ribs）：** 支撑性任务在每个活动下纵向展开，通过位置体现优先级。

**从左到右、从上到下的构建策略：** 跨所有主要功能增量构建，而不是把一个功能做完做透再做下一个。

### 为什么有效

- **可视化沟通：** 故事地图常作为信息辐射源展示，让团队始终聚焦全局
- **叙事结构：** 按用户工作流组织，而非按技术架构
- **发布规划：** 横向切片能揭示 MVP 与增量发布
- **缺口识别：** 暴露扁平需求池会掩盖的缺失功能

### 反模式（这不是什么）

- **不是甘特图：** 故事地图展示的是优先级，不是时间估算
- **不是技术架构：** 地图跟随用户工作流，而不是系统分层（界面 → 接口 → 数据库）
- **不是项目计划：** 它是发现与沟通工具，不是排期表

### 何时使用

- 启动新产品或重要功能时
- 重构现有需求池时（从扁平清单变为可视化地图）
- 让相关方就范围与优先级达成一致时
- 规划 MVP 或增量发布时

### 何时不要使用

- 单一功能项目（用故事地图是杀鸡用牛刀）
- 需求池已经梳理清楚并排好优先级时
- 纯技术重构工作（没有可映射的用户工作流）

### 引导式对话的唯一事实来源

本技能默认以 [`workshop-facilitation`](../workshop-facilitation/SKILL.md) 作为交互协议。

它定义了：
- 会话预告 + 进入模式（引导模式、背景倾倒、最佳推测）
- 每轮只问一个问题的对话节奏，提问使用平实语言
- 进度标签（例如「背景 Qx/8」「评分 Qx/5」）
- 打断处理与暂停/继续行为
- 决策点处给出编号建议
- 常规问题提供可快速选择的编号选项（必要时包含「其他（请说明）」）

本文件定义领域专属的评估内容。若两者冲突，以本文件的领域逻辑为准。

## 应用

本交互型技能最多提出 **5 个自适应问题**，每步提供 **3-4 个编号选项**。

引导议程与产出检查清单请使用 `template.md`。

交互模式：若想要一步一步来的对话流（决策点有编号建议、常规问题有快速选项），可配合 `skills/workshop-facilitation/SKILL.md` 使用。如果用户要求一次性输出，则跳过多轮引导。

### 第 0 步：收集背景（提问之前）

**AI 助手建议：**

在创建故事地图之前，我们先收集一些背景：

**产品/功能背景：**
- 你要映射的是什么系统或功能？
- 产品构想、PRD 草稿或现有需求池
- 官网文案、定位材料或用户流程
- 现有用户故事（如果你正从扁平需求池转型）

**用户背景：**
- 目标用户画像或用户分层
- 用户研究、访谈或用户旅程图
- 待办任务（JTBD）或问题陈述

**你可以直接粘贴这些内容，也可以简单描述一下系统。**

---

### 问题 1：界定范围

**AI 助手问：**

"你要映射什么？（范围是什么？）"

**提供 4 个编号选项：**

1. **整个产品** —— "从发现到完成的完整端到端系统"（新产品或全面重做时常见）
2. **主要功能领域** —— "较大产品中的某个具体工作流（如'新手引导''下单结算''报表'）"（功能上线时常见）
3. **用户旅程** —— "某个具体用户目标或待办任务（如'雇一个装修队''报税'）"（JTBD 驱动的地图常见）
4. **重构/改版** —— "正在重建或简化的现有产品/功能"（老系统现代化时常见）

**或者描述你的具体范围。**

**用户回答：**【选择项或自定义】

---

### 问题 2：识别用户/画像

**AI 助手问：**

"这张地图的主要用户是谁？（列出画像或用户分层。）"

**提供 4 个编号选项：**

1. **单一画像** —— "只有一类主要用户（如'小企业主'）"（简化映射，适合 MVP）
2. **多画像、共享工作流** —— "不同类型用户走同一套核心活动（如'买家'和'卖家'都要浏览商品列表'）"（平台型产品常见）
3. **多画像、不同工作流** —— "不同类型用户有各自独立的工作流（如'管理员' vs '终端用户'）"（需要分开画地图或用泳道）
4. **组织内不同角色** —— "不同职能岗位（如'产品经理''设计师''工程师'）"（内部工具常见）

**或者描述你的用户。**

**适配：** 使用第 0 步提供的画像（原型画像、JTBD 等）

**用户回答：**【选择项或自定义】

### 问题 3：生成主干（活动）

**AI 助手说：**

"我们来搭建主干——用户为实现目标而执行的一系列活动构成的叙事流。"

**AI 助手根据范围（Q1）和用户（Q2）生成 5-8 个活动**，按工作流顺序从左到右排列。

**示例（若范围 = "电商结算"）：**

```
主干活动（从左到右）：

1. 浏览商品
2. 加入购物车
3. 查看购物车
4. 填写收货信息
5. 选择支付方式
6. 提交订单
7. 收到订单确认
```

**AI 助手问：**

"这条主干是否覆盖了完整工作流？需要增加、删减还是调整活动顺序？"

**用户回答：**【确认、修改或增加自定义活动】

---

### 问题 4：生成用户任务（挂在每个活动下）

**AI 助手说：**

"现在我们在每个活动下添加用户任务，按优先级组织（顶部 = 必须有，底部 = 锦上添花）。"

**AI 助手为每个活动生成 3-5 个用户任务**，按优先级纵向排列。

**示例（针对活动 2："加入购物车"）：**

```
加入购物车（活动）
├─ 把单件商品加入购物车（必须有，行走骨架）
├─ 调整数量（必须有）
├─ 批量加入多件商品（应该有）
├─ 收藏商品稍后买（锦上添花）
└─ 添加礼品包装（锦上添花）
```

**AI 助手对所有主干活动重复此步骤**，展示完整地图。

**AI 助手问：**

"这覆盖了关键任务吗？优先级对吗（顶部 = MVP，底部 = 后续发布）？"

**用户回答：**【确认、修改或增加自定义任务】

### 问题 5：识别发布切片（行走骨架 + 增量）

**AI 助手说：**

"我们通过在地图上画横线来定义发布切片。"

**发布 1（行走骨架）：** 所有活动中优先级最高的任务——最小端到端功能

**发布 2（下一增量）：** 第二优先级的任务，增强核心工作流

**发布 3（完善/扩展）：** 第三优先级的任务（锦上添花、边界情况、优化）

**示例：**

- 主干跟随用户叙事（而非技术分层）
- 行走骨架交付端到端价值
- 增量发布在不破坏核心流程的前提下逐步提升完善度

### 示例 2：坏的故事地图（技术分层）

**主干（错误）：**
```
界面层 → 接口层 → 数据库层 → 部署
```

**为什么失败：**
- 不以用户为中心（用户不关心技术架构）
- 无法增量交付端到端价值
- 是披着故事地图外衣的瀑布式思维

**修复：**
- 按用户工作流画地图："注册 → 配置设置 → 邀请团队 → 创建项目"
- 每个发布交付完整工作流，而不是单一技术层

## 常见陷阱

### 陷阱 1：伪装成故事地图的扁平需求池
**症状：** 故事地图只是一张纵向清单，没有横向叙事

**后果：** 丧失沟通价值，依然是"脱离上下文的碎料"

**修复：** 强制横向结构——活动横贯顶部，任务纵向展开

---

### 陷阱 2：拿技术架构当主干
**症状：** 主干 = "前端 → 后端 → 数据库"

**后果：** 不以用户为中心，无法增量交付价值

**修复：** 主干应跟随用户工作流，而不是系统分层

---

### 陷阱 3：功能做完再做下一个（瀑布式）
**症状：** 发布 1 = "把活动 1 做完"，发布 2 = "把活动 2 做完"

**后果：** 所有活动都完成前，端到端价值为零

**修复：** 行走骨架 = 横切所有活动的薄片，再逐步增强

---

### 陷阱 4：太早陷入过多细节
**症状：** 一上来就想把每个边界情况和验收标准都映射出来

**后果：** 分析瘫痪，丢掉全局

**修复：** 先画主干 + 高层级任务，细节以后再说

---

### 陷阱 5：地图被藏进工具里
**症状：** 故事地图只放在项目管理工具（如 TAPD、禅道）或在线白板里，从不展示

**后果：** 丧失作为信息辐射源的价值

**修复：** 把地图打印出来贴墙上，让团队每天都能看到
